# Hub command contract (shared by UI, MCP and tests)

Single source of truth: `halp-core` exposes a command registry. Every capability is a command.

## Envelope
Request:  `{ "command": "tasks.create", "args": { ... }, "request_id": "<ulid>" }`
Response: `{ "ok": true, "result": { ... } }` or
          `{ "ok": false, "error": { "code": "not_found|invalid_args|denied|confirmation_required|conflict|internal", "message": "...", "confirmation_id": "<ulid?>" } }`

Tauri: `invoke("dispatch", { request })` returns the response. Change events are emitted on the Tauri event `halp://event`.
MCP: each command with `mcp: true` is a tool named after the command with dots replaced by underscores (`tasks.create` → `tasks_create`). Its args are the inputSchema and its result is the structuredContent. See MCP.md.

## Command descriptor (from `commands.list`)
`{ name, description, tier: "T0"|"T1"|"T2"|"T3", input_schema, output_schema, data_class, user_only, mcp }` (the last three since v1.3)

The machine-readable copy is `hub/docs/fixtures/commands.json`. It is the output of `halpd schema`: the descriptors sorted by name, wrapped as `{"commands": [...]}`. A halp-core test fails when the fixture is out of date, so regenerate it after changing a command (`halpd schema > docs/fixtures/commands.json`).
Tiers: T0 read, T1 reversible local write, T2 external side effect, T3 destructive/privileged.

## Event
`{ id, ts, actor: "user"|"agent:<client>"|"module:<id>"|"integration:<id>"|"system", command, entity: { kind, id }, summary }`

## Core entities (JSON)
- Item: `{ id, parent_id|null, order, kind: "bullet"|"task", status: "todo"|"in_progress"|"done", title, notes, tags[], due|null (YYYY-MM-DD), type_id|null, fields{}, created_at, updated_at, version }`
- TaskType: `{ id: "dev.pull_request", title, icon, schema (JSON Schema 2020-12), display: { primary_fields[], badge_field? } }`
- Layout: `{ id, role_id, columns: 12, widgets: [ { id, kind, title, x, y, w, h, config{} } ] }`
- Role: `{ id: "developer"|"eng-manager"|"cso", title, accent, layout_id, task_types[], widgets[] }`
- DayState (`day.state`): `{ date, role, focus: Item|null, counts{overdue,today,in_progress}, agenda[], layout }`

## Initial command set (P0)
tasks.create, tasks.get, tasks.list (filter: type_id, status, tag, due_before, due_after, text, parent_id, limit), tasks.update, tasks.move, tasks.complete, tasks.delete (T3), history.undo, history.redo, history.list,
types.list, types.get, types.define (T1),

role.list, role.get, role.switch, focus.get, focus.set, focus.clear, day.state, capture.quick (parses "Fix login #bug due:friday"), commands.list.

## Amendments v1.1 (lead, after frontend P2 foundation) — binding for core
1. Consent commands: `consent.list`, `consent.get {id}`, `consent.approve {id}`, `consent.deny {id}` + event `consent.requested`. Only actor `user` may approve/deny. Approved command executes as the ORIGINAL requesting actor. Denied → original request returns error `denied`.
2. `history.undo` / `history.redo` accept optional `event_id` (selective undo of that event if no conflict; else error `conflict`).
3. Results are objects: tasks.list→{items}, role.list→{roles}, commands.list→{commands}, history.list→{events}, types.list→{types}, role.switch→{role,layout}, focus.*→{focus}, capture.quick→{item,parsed}, history.undo/redo→{event}, tasks.delete→{deleted}.
4. Arg shapes: tasks.update {id, patch}, layout.update_widget {widget_id, patch}, layout.move_widget {widget_id, x, y}, layout.add_widget {kind, title, w, h, config?}, history.list {limit, actor_prefix?}.
5. Grid collision rule (same as hub/app/src/lib/layout/grid.ts): clamp into 12 cols; moved widget pinned; overlapping widgets pushed down; then vertical compaction.
6. commands.list input_schema must include `required`.
7. Focus is per role; day.state reflects the active role's focus.
8. Role scoping of tasks: an item belongs to roles via field `roles: string[]` (empty = all roles); tasks.list accepts `role` filter. (Mock uses @dev/@em/@cso tags — the UI will switch to `roles`.)

## Core notes v1.2 (halp-core implementation) — additive, binding for core and clients
1. Error code `conflict` (added above): stale `tasks.update` `if_version`, an undo/redo (selective or not) whose entities changed since, or a `types.define` that reuses a built-in/pack type id.
2. Item adds two fields: `roles: string[]` (amendment 8) and the read-only `inherited_tags: string[]` (ancestor tags not already on the item, nearest ancestor first; the `tag` filter matches them).
3. tasks.list filter: `status` takes one status or an array; `parent_id: null` = root items only; `due_before` / `due_after` are exclusive and exclude undated items; `role` keeps items with that role or no roles (an item with no roles of its own takes its nearest ancestor's); `kind`; `limit` default 200, max 1000.
4. Arg aliases accepted: `consent.* {confirmation_id}` for `{id}`, `role.get/role.switch {role_id}` for `{id}`, `focus.set {item_id}` for `{id}`, `tasks.move {order}` for `{index}`. All layout commands take optional `role_id` (default: the active role).
5. tasks.create / tasks.update `due`: `YYYY-MM-DD` or natural language (`friday`, `tomorrow`, `+3d`), resolved against the user's local date. `tasks.update {id, patch, if_version?}`; nullable patch fields (`due`, `type_id`) take `null` to clear. Status cannot be set on bullets or on tasks with subtasks (it is derived).
6. tasks.complete `{id, done?=true, cascade?=false}` returns the Item; `done:false` reopens to `todo`. A bullet or a task with subtasks needs `cascade:true` (completes the whole subtree).
7. tasks.delete `{id}` → `{deleted: [ids]}` (the subtree, pre-order). It also clears any role's focus pointing into it. Undo restores everything.
8. history.undo/redo → `{event, history_event}`: `event` is the undone/redone event, `history_event` the new `history.undo`/`history.redo` event; both `null` when there was nothing to do. An `event_id` that is not on the stack is `not_found`.
9. history.list `{limit?=50 (max 500), before?, actor_prefix?}` → `{events: [Event + seq, causation_id, undoable], can_undo, can_redo}`.
10. role.list → `{roles, current}`. role.switch and focus.set/clear are logged but **not undoable** (view state); undo skips them.
11. layout.add_widget `{kind, title?, x?, y?, w?=4, h?=3, config?, role_id?}` → the updated Layout (new widget id `w-xxxxxxxxxx`). `kind` must be one of the role's widget kinds. Without x/y it goes in the first free slot in reading order. layout.update_widget patch: `{title?, config?, x?, y?, w?, h?}`. All layout commands return the Layout.
12. capture.quick `{text, parent_id?, tags?, kind?, top?}`. The default parent is a root bullet "Inbox" (tag `inbox`), created on first use. The item gets `roles: [active role]`. An unparseable `due:` token stays in the title and `parsed.due` is `null`.
13. types.define args are the TaskType itself → `{...TaskType, origin: "user"}`; types.list → `{types: [{...TaskType, origin: "builtin"|"pack"|"user"}]}`.
14. Consent: consent.list → `{pending: [{id, command, tier, actor, args, summary, created_at}]}` (oldest first); consent.get → one of those; consent.approve → the approved command's result; consent.deny → `{denied: id}`. Pending requests are kept in memory and dropped on restart (= denied). Events: `consent.requested` (actor = requester), `consent.approve` / `consent.deny` (actor `user`), all with entity `{kind: "confirmation", id}`. (v1.3: the policy is always the policy engine; see the v1.3 notes.)
15. Every object `input_schema` in commands.list carries `required` (possibly `[]`).
16. TUI import (the `import.tui` command, sent by `halpd import`) records one undoable event, command `import.tui`, entity `{kind: "import", id: "tui"}`.

## Core notes v1.3 (P1: policy and MCP), additive and binding for core and clients
1. **Policy.** Every call from every actor is checked by the policy engine (`halp-policy`). `user`/`system`: T0–T2 run and T3 is always confirmed, so the UI's own `tasks.delete` gets `confirmation_required` as well, and the UI confirms it in place. Agents: see MCP.md, "Policy". Some arguments raise the effective tier: an agent's undo or redo that deletes items is T3, a redo that re-applies a T3 change is T3, and an agent removing the `activity` widget is T2.
2. **User-only commands** (`user_only: true`, `denied` for anyone else, never MCP tools): `clients.*`, `grants.*`, `rules.*`, `policy.clear_taint` (v1.4), `history.purge`, `import.tui`, `consent.approve`, `consent.deny`.
3. **clients.pair** `{name, id?}` returns `{client: ClientView, token}`. The token is shown once, and only its SHA-256 is stored. `ClientView` is `{id, name, actor: "agent:<id>", created_at, revoked_at|null, grants: {t1, data_classes[]}}`. **clients.list** `{}` returns `{clients}`. **clients.revoke** `{id}` returns the ClientView. Revoking takes effect on the next call, even across processes, deletes the client's rules, and makes its pending requests unapprovable.
4. **grants.list** `{client_id?}` returns `{grants: [{client_id, grants: {t1, data_classes}}], data_classes: [all known classes]}`. **grants.set** `{client_id, t1?, data_classes?}` returns the ClientView. Data classes: `general` (default), `notes.private`, `email.body`, `secrets`, `audit`.
5. **rules.create** `{client_id, command, args: {name: exact value}}` takes a T2, non-user-only command and at least one argument, and returns the Rule. **rules.list** `{client_id?}` returns `{rules}`. **rules.delete** `{id}`. A rule lets that one client run that command with exactly those top-level argument values without asking, as long as the client is not tainted.
6. **audit.list** `{limit?=100 (max 1000), before?, actor_prefix?}` returns `{records: [{id, ts, actor, command, tier, args_hash, decision, reason, approver|null, confirmation_id|null, tainted}]}`, newest first. `decision` is one of `allow`, `deny`, `confirm`, `approved`, `failed`, `denied`, `expired` or `superseded` (v1.4). Agents need the `audit` data class. Allowed user and system T0 calls are not recorded.
7. **history.purge** `{older_than_days?, deleted_items?=false, remember?=false}` (T3) returns `{redacted, retention_days|null}`. It redacts events in place (payload, inverse and summary; the row and its metadata stay) and removes them from the undo and redo stacks. `remember` stores the retention, and `older_than_days: 0` with `remember` clears it.
8. **history.list** also takes `after: <event id>`, which returns the events since that one, oldest first (a change feed). It cannot be combined with `before`.
9. **capture.parse** `{text, tags?, kind?}` (T0) returns `{title, tags, due|null, kind, status}`. It is exactly what `capture.quick` would store, with nothing written. Use it for live previews.
10. **import.tui** `{content_base64, file_name?, passphrase?, utc_offset_minutes?}` (T3, user only). It returns `{format, items, roots, skipped_deleted, warnings}`. `skipped_deleted` counts the tombstones; they are not in the outline. Deleted TUI items are kept as hidden tombstones (see ARCHITECTURE.md).
11. **Consent v1.3.** A pending request also has `args_hash`, `details`, `tainted`, `taint_source|null` and `expires_at`. It expires 5 minutes after `created_at`, which counts as a denial. Its `args` are for display: secrets and file content are replaced (v1.4: otherwise in full; see `display_truncated`). Arguments are validated before a request is parked. Approving runs the command as the original actor and records the approval together with its outcome.
12. **Packs.** Every role pack offers the `activity` widget (recent agent and user events from `history.list`). An agent removing it is T2.

## Core notes v1.4 (security review fixes), additive and binding for core and clients
1. **Full consent args.** `PendingConsent.args` (in `consent.list` and `consent.get`) is the whole canonical request that will run, with only secrets (`passphrase`) and imported file content (`content_base64`) replaced by placeholders. The new field `display_truncated: bool` is `false` then. When the args exceed 64 KiB of canonical JSON, `args` is the short audit form (long strings cut, or `{truncated, bytes, sha256}`) and `display_truncated` is `true`. `consent.list` also keeps a 1 MiB budget for args per answer; entries past it carry the short form with `display_truncated: true`, and `consent.get` returns them in full. **A client must not offer approval while `display_truncated` is `true`**; call `consent.get` first. The `consent.requested` event payload is `{confirmation_id, command, tier, args (short form), display_truncated}`.
2. **Scope check on approval.** `consent.approve` can return `conflict` with message `the request changed since you saw it: …` and a **new** `confirmation_id`. That means what the request would touch changed since it was shown (an item moved under the item being deleted, a newer change to an undo's entities, more events for a purge). Nothing ran. The old id is gone, and the same request is pending again under the new id with a fresh `summary` and `details` and a new `consent.requested` event. Clients show the new request, not an error. The audit log gains decision `superseded`, and the event log gains `consent.superseded` (actor `user`, entity `{kind: "confirmation", id: <old id>}`). An approve whose request can no longer run returns its error and settles the request as `failed`.
3. **Approval is in-process only.** The socket's user channel accepts `consent.list`, `consent.get` and `consent.deny`; `consent.approve` there is `denied`. `halpd consent approve` is refused with a pointer to the Hub window.
4. **Taint per client.** Taint is tracked per actor across all its sessions. It clears 30 minutes after the client's last tainted read. **policy.clear_taint** `{client_id}` (T1, user only, not an MCP tool) clears it now. It returns `{client_id, was_tainted_by: string|null}` and records a `policy.clear_taint` event (entity `{kind: "client", id}`). `not_found` means an unknown client.
5. **One Core per database.** Opening a database that another process has open fails with `conflict: HalpTask Hub is already running; use the agent socket (halp-mcp) instead`. A commit whose rows changed underneath it fails with `conflict`.

## Core notes v1.5 (P3: integrations), additive and binding for core and clients
1. **Commands.** `integrations.list` (T0), `integrations.sync_now` (T1), `context.capture` (T1), `integrations.connect` (T2, user only), `integrations.disconnect` (T3, user only), and the hidden integration write path `ext.upsert` / `ext.status` (T1, `integration:<id>` actors only). Shapes, limits and behaviour are in INTEGRATIONS.md.
2. **Synced items** carry `origin: "integration:<id>"` and live under a per-integration root bullet. Items removed remotely are tagged `archived` (leaf tasks set `done`), never deleted; clients should hide `archived` items in integration widgets. New built-in type `ext.issue`.
3. **Tokens** are never command arguments. The app sets them with the Tauri command `integrations_set_token {id, token}` (resolves to nothing or rejects with an error code string: `not_running`, `unknown_integration`, `empty`, `too_long`, `not_printable_ascii`, `keychain_error`, `internal`). `integrations.list` shows only `has_secret`.
4. **Events.** `ext.upsert` writes a normal history event as `integration:<id>`. State changes appear as `integrations.status` events with payload `{id, state, error}`.

## Core notes v1.6 (second security review), additive and binding for core and clients
1. **Data classes per type.** A type schema may carry `"x-halp-data-class": "<class>"`; without it the type is `general`. Items inherit the first non-`general` class from their type or an ancestor. An agent without the class in its grants gets `not_found` for `tasks.get`, any write naming such an item or creating one (`tasks.create|update|move|complete|delete`, `capture.quick`, `focus.set`, an undo or redo touching one), and such items are left out of `tasks.list`, `day.state`, `focus.get` and the MCP resources built on them. The user is unaffected. Events about a private item have summary `"<Verb> a private item"` and args `{"private": true}`; a parked request on one has summary `"Asked: <command> on a private item"`, and its `consent.requested` payload is `{confirmation_id, command, tier, private: true}` (no args). `consent.list` / `consent.get` still show the user the full args.
2. **Taint through writers.** Reading an item, a widget (title or config) or an agent-defined type taints an agent with every non-user actor that wrote it, not only its `origin`. Built-in and pack types never taint. Results of approved requests taint the requesting agent like direct reads.
3. **Queue cap.** `MAX_PENDING_TOTAL` (64) counts only agents' and modules' requests; the user's own T3 requests always park.
4. **Pinned at park time.** A parked `capture.quick` gets the Inbox's `parent_id` if it had none, and parseable natural-language dues (`tasks.create.due`, `tasks.update.patch.due`, `due:` words in capture text) are rewritten to `YYYY-MM-DD`. `consent.get` shows the pinned args.
5. **Format characters.** Titles, tags, notes, labels and widget titles reject bidi and other invisible format controls (U+200B, U+200E/F, U+202A–E, U+2060–64, U+2066–6F, U+FEFF, U+00AD, tag characters, …) with `invalid_args`; ZWJ (U+200D) and ZWNJ (U+200C) stay allowed. The TUI importer strips them instead.
6. **User channel.** The socket's user channel also accepts `clients.list` and `clients.revoke` (it still refuses `consent.approve`, `clients.pair`, `grants.set` and `rules.*`). `halpd clients list|revoke` use it while the Hub runs. `halpd serve --interactive` approves only when the user types the 4-character code shown (last 4 characters of the confirmation id), ignores input typed before the prompt, and offers only deny when `display_truncated` is true.
7. **Desktop shell (`key_status` and `halp://key`).** `{state: "ready"}` now carries the MCP host's state: both `mcp` and `mcp_error` absent while it starts, then either `mcp: {socket}` or `mcp_error: string`, re-sent on `halp://key` (the UI must not treat a second `ready` as a new unlock). A parked request brings the main window to the front at most once per 10 s per actor; the OS attention flag and the tray count still update on every consent event.

## Core notes v1.7 (P4: calendar), additive and binding for core and clients
1. **New integration kind `calendar`** (`INTEGRATION_KINDS` gains it). Settings, sources (`ics`, `mcp`), mapping to `dev.meeting` / `em.meeting`, categories and 1:1 linking are in INTEGRATIONS.md.
2. **The ICS feed URL is a secret.** It is set with `integrations_set_token {id, token: <url>}` and kept in the keychain, never in `settings`, events, history, audit or status. `integrations_set_token` gains the error code `invalid_url` (calendar `ics`: not an https or `webcal` URL; `webcal://` is stored as `https://`). The shell should add a Tauri command `integrations_secret_hint {id}` → `string|null` over `Runtime::secret_hint`, which returns `host …last4`; the UI shows only that.
3. **Proposed: `ext.patch_fields`** `{id, type_id, if_version?, fields}` (T1, hidden, `integration:<id>` actors only, added to the policy's integration writes). It merges `fields` into an existing item's fields and validates the result against the type schema. Only fields the type lists in `"x-halp-ext-writable": [...]` may be named (the EM pack would list `["scheduled_for"]` on `em.one_on_one`), only `general`-class items, `conflict` when `if_version` is stale, `not_found` when the item or type does not match. It writes a normal history event as `integration:<id>`. The calendar connector calls it to move an open 1:1's `scheduled_for`, and treats `unknown command` as "not available yet".
4. **Proposed: `email` on `em.person`** (`{"type": "string", "format": "email", "maxLength": 254}`). With it, 1:1 linking matches people by address instead of by name.
5. **Items from one connector, two types.** With both `item_types`, a meeting is written twice (once per type) and both copies get the integration's `roles`. Until `ext.upsert` items can carry their own `roles`, a user with both packs sees a meeting in both; connect with one type per pack to avoid it.

## Core notes v1.8 (P4 follow-ups and third security review), additive and binding for core and clients
1. **`ext.patch_fields`** (replaces the v1.7 proposal) `{id, type_id, if_version?, fields}`: T1, hidden, `integration:<id>` actors only (in the policy's `INTEGRATION_WRITES`); `denied` for agents and the user. It merges `fields` into an existing item and validates the result against the type schema. The integration must own the item: its `origin` is that integration's actor **and** it has an external link from that integration. Only fields the type lists in `"x-halp-ext-writable"` may be named, and that key counts only on built-in and pack types (never on `types.define` types). Only `general`-class items: a private item, a wrong `type_id`, or an item the integration does not own is `not_found`; a stale `if_version` is `conflict`. It writes a normal history event as `integration:<id>`. `em.one_on_one` lists `["scheduled_for"]`.
2. **Per-item roles on `ext.upsert`.** An item may carry `roles: [...]`. It must be a non-empty subset of the integration's configured `roles` (it can narrow, never widen; duplicates are dropped); without it the item gets the integration's roles. The calendar connector narrows `dev.meeting` items to `developer` and `em.meeting` items to `eng-manager` when connected for that role, which resolves v1.7 note 5.
3. **`email` on `em.person`**: `{"type": "string", "format": "email", "maxLength": 254}`. 1:1 linking matches people by address first.
4. **`clients.list`** entries gain `last_seen` (the client's last call) and `tainted_until` (when its taint clears), both RFC 3339 or `null`. They come from the policy's memory, so they are `null` after a Hub restart until the client calls again.
5. **Consent.** A pending request gains `private: bool`. On the socket's user channel (`halpd consent`) a private request is shown with `args: null`, `display_truncated: true`, empty `args_hash` and `details`, and summary `"<command> on a private item (open the Hub to see it)"`; the Hub window still sees it in full. A request with `display_truncated: true` cannot be approved by anyone: `consent.approve` is `denied` ("too large to show in full … deny it") and the request stays pending. MCP hosts expire overdue requests every 15 s.
6. **Text checks.** Typed `fields`, widget `config` (`layout.add_widget`, `layout.update_widget`) and `types.define` schemas reject C0/C1 controls (except line feed and tab) and the format characters of v1.6 note 5 in every string and key, with `invalid_args`. The format set gains U+E0100–E01EF (variation selectors supplement); single-line text (titles, tags, labels) also rejects U+2028 and U+2029. Clients show consent args with every hidden character escaped as `\uXXXX`.
7. **Private data, read side.** `history.list` for anyone but the user redacts summaries of events about items that are private *now* (`"<Verb> a private item"`), even if they were general when written. `capture.quick` without `parent_id` checks the data class of the Inbox it would file into, so a private Inbox needs the grant (`not_found` otherwise).
8. **Socket.** Connections use separate pools: unauthenticated (8, auth line within 2 s), agent (16, at most 4 per client) and user channel (2). A full pool answers `ERR busy` and closes. MCP subscriptions to `halp://task/{id}` are refused (`resource_not_found`) unless the client may read that item.
9. **Desktop shell.** `integrations_secret_hint {id}` → `string|null` (the stored secret's hint, e.g. `calendar.example.com …abcd`, never the secret; `null` when nothing is stored, the runtime is not running or the id is unknown). `integrations_set_token` may reject with `invalid_url` (v1.7 note 2).

## Core notes v1.9 (CSO pack in the core, review leftovers), additive and binding for core and clients
1. **`x-halp-immutable-when`** (schema annotation, counted only on built-in and pack types, like `x-halp-ext-writable`): an object of 1–8 schema properties, each mapped to 1–16 scalar values, e.g. `{"status": ["approved"]}` on `cso.evidence`. An item is *locked* when every listed field holds one of its values (conditions are ANDed). Pack loading rejects a malformed annotation. The core enforces it at every write: `tasks.*`, `capture.*`, `history.undo`/`history.redo`, `ext.upsert` and `ext.patch_fields`.
   - **Only the user may lock an item.** An agent or integration that would create an item locked, or change one into the locked state, is `denied` ("… only the user can do that").
   - **Locked is terminal.** Nobody can change a locked item back out of the locked state, not even the user and not by undo: there is no un-approve. A mistake is fixed by appending a new approval with another decision, or by deleting the item (T3) and creating a new one. So `sha256` never changes once approved.
   - **Agents and integrations** cannot change, complete, move or delete a locked item, or delete an ancestor of one. `tasks.update`/`complete`/`move`/`delete` and undo/redo are refused at once with `denied`, before any confirmation is parked.
   - **The user** may move and delete a locked item, and may change its `fields` only by appending to array fields (`approvals`); every other field, the title, notes, tags, due, status and type stay as they are. Sibling `order` renumbering and `updated_at`/`version` are not changes.
   - Undo and redo check the event's changes against the same rules: the user's undo of an approval, or of an appended approval, is `denied`; undoing the user's delete of a locked item restores it.
   - `ext.upsert` reports a locked item per item in `rejected` (`"the item is immutable in the Hub …"`) and leaves it unchanged; `complete: true` never archives a locked item. `ext.patch_fields` on a locked item is `denied`. Messages name the item id and type, never its title.
2. **`ext.upsert` and data classes.** An item whose `type_id` is of a class other than `general` (e.g. `em.private_note`) is `rejected` ("this type cannot be written by integrations"). A linked item whose current class is not `general` (for example the user moved it under a private parent) is left alone and counted in `skipped`, with no reason given; `complete: true` does not archive it either. A new item is skipped the same way when its root would not be `general`.
3. **`cso.board_brief`** is of class `cso.unpublished`: agents without that grant do not see it (`tasks.list` omits it, `tasks.get`/`update` and `tasks.create` of that type are `not_found`). Clients and the mock treat any type whose schema names an `x-halp-data-class` other than `general` the same way, item and ancestors included; only `notes.private` is also kept out of the user's text search.
4. **MCP prompts** are generated at build time from every built-in pack's `prompts/*.md` (halp-mcp `build.rs`); a test checks that every file on disk is served. The CSO pack adds `prepare-board-brief` and `evidence-gap-check`.
5. **Variation selectors in single-line text** (titles, labels): U+FE00–FE0D are refused; U+FE0E and U+FE0F are allowed only directly after a visible character, so a run of two or more, or one at the start or after a space or control, is `invalid_args` ("… variation selector U+XXXX here (one U+FE0E or U+FE0F directly after a symbol is allowed)"). `sanitize_title` drops them. The frontend's `formatCharProblem` applies the same rule.
6. **`capture.quick` / `capture.parse`** return the real title error (e.g. hidden characters) as `invalid_args`; only text that is empty after parsing gives `nothing to capture`.
7. **Pack text checks.** Pack-loaded layouts (widget config included), type schemas and type titles, icons and display settings go through the same control and format character checks as `types.define` (v1.8 note 6). A pack that fails is not loaded.
8. **Standing rules** are unchanged: only agent-callable T2 commands (`tier: "T2"`, not `user_only`, `mcp: true`). The core has none today; Settings > Rules shows an empty state saying so, and its form lists any that packs or extensions add.

### Review fixes: `ext.upsert` complete batches, `ext.patch_fields` text

- In a `complete: true` batch, an item rejected by validation, or a duplicate, still counts as listed upstream: it is never archived. If any item has no usable `external_id` (empty, too long, control characters, or the reserved root id), the batch is treated as incomplete: nothing is archived, and the result carries a `note` saying so (`UpsertResult.note`, omitted otherwise).
- `ext.patch_fields` rejects values with control or invisible format characters (`invalid_args`, same check as typed fields), instead of storing them.

## Core notes v1.10 (P5-B: installed packs), additive and binding for core and clients
1. **Commands.** All `packs.*` writes are `user_only` and `mcp: false`: an agent gets `denied` for each, before any confirmation. Only `packs.list` and `packs.get` are agent-readable (T0, MCP); agents get the row without the user-only fields (`description`, `publisher`, `previous_version`, `error`). Tiers: `list`, `get`, `preview`, `keys_list`, `dev_get` T0; `disable`, `reset_layout`, `dev_reload` T1; `install`, `enable`, `rollback`, `uninstall`, `keys_add`, `keys_revoke`, `dev_set` T3. `packs.dev_set {path}` takes `path` as required and nullable (null turns dev mode off; a missing key is `invalid_args`). Shapes are in `app/src/lib/api/types.ts` (PacksCommandMap) and `docs/fixtures/commands.json`.
2. **`PackView`**: `{id, version, title, role_id, trust, enabled, extends (nearest first), key_fp, capabilities, status, description?, publisher?, previous_version?, error?}`. `trust` is `builtin | first_party | community | unsigned | dev`. `key_fp` and `PackKey.fingerprint` are 64 lowercase hex without spaces (the UI groups them); `key_id` is the first 16. `status`: `ok`, `disabled`, `error` (the stored bundle failed re-verification or the pack failed to load), `blocked` (needs a newer Hub, or a pack it extends is missing or not loaded). `packs.list` sorts built-in packs first, then installed, then dev. Built-in (`halp.*`) packs cannot be disabled, uninstalled, rolled back or replaced (`conflict`); dev packs follow the dev folder (`conflict`).
3. **Install.** `packs.preview {bundle_base64}` verifies and dry-runs and returns a `preview_id` (`pv_…`) bound to the bundle's SHA-256, valid 10 minutes, at most 4 kept; nothing is installed. `packs.install {preview_id, trust_key?}` installs exactly those bytes; an unknown id is `not_found`, an expired one `conflict`; a preview is used once.
   - **Signatures.** A bad signature is an error, never unsigned. `signature` is `verified`, `unknown_key` or `none` (the core never sends `invalid`). An unsigned pack with privileged annotations (`x-halp-immutable-when`, `x-halp-ext-writable`), modules or UI widgets is `denied`. A pack signed by an untrusted key previews with `trust: "unsigned"` when it loads unsigned, or with `trust: "community"` and a warning when it only loads with that key trusted; install then needs `trust_key: true` (without it `denied`, with a hint), which trusts the key (`label` = publisher name) in the same step.
   - **Updates.** A version that is not newer is `conflict` (use `packs.rollback`). The key is pinned: an update signed by another key, or unsigned, of a signed pack is `denied`. The pack's `min_hub` must match the Hub (0.1.x). Migrations (`migrations[]` in the manifest) run on every item of the pack's types; if any item would fail validation, or a locked item would change, the update is refused with `conflict` naming up to 50 item ids, and nothing changes. The preview reports the same as `migrations.items_failed`/`failed_ids` and a warning. Migrated items are written as the actor `module:<pack_id>` (an agent that reads one is tainted by it, like any writer).
   - **Rollback** returns to `previous_version` (one step) and restores the items the update migrated; it is `conflict` if one of them changed since. **Uninstall** is `conflict` while another installed pack extends it. A change that would stop another loaded pack (other than one it targets) is `conflict`; `keys_revoke` is exempt and disables what it must.
4. **Pack events are not undoable.** Every `packs.*` write except `reset_layout` is recorded with `undoable: false`: `history.undo` (by the user or an agent) skips them, so an agent cannot re-enable a pack the user disabled. `reset_layout` is an ordinary undoable layout change. Events carry no bundle or manifest text. A pack that fails to load at startup or after a change is reported by a system event `packs.status` (`{id, status}`) and in the Hub's warnings; startup never fails because of a pack.
5. **Storage and re-verification.** The bundle is stored whole, encrypted, keyed by SHA-256 (store schema v4: `pack_blobs`), with the pack record (current and previous version, trust, key id, own types, migrated items) and trusted keys. Every load re-hashes the blob and re-verifies the signature against the current keys; a mismatch or a revoked key puts the pack in `error` and retires its types.
6. **Task type origin (trust split).** `types.list`/`types.get` rows carry `origin`: `builtin | pack | user | retired`; `pack` and `retired` rows also carry `trust` and `pack` (the pack id). Only `builtin`, `first_party` and `community` trust counts privileged annotations (`may_annotate`); an `unsigned` or `dev` type never locks or opens fields to integrations.
7. **Retired types.** A type whose pack was uninstalled, disabled, failed verification, or whose dev folder went away is `retired` and keeps its last definition and trust (`retired_types` table, survives restarts). `tasks.create` of a retired type (and moving an item to one) is `invalid_args` ("type … is retired"). Existing items keep their data class (private-class items stay `not_found` to agents without the grant) and their lock rules (locked items stay locked). The user may edit them, validated against the last definition, and may set `type_id` to null when `fields` is empty. A pack can never take over a user type id, another pack's type, or a retired type of a different data class or (from a non-annotating trust) one with privileged annotations: `conflict`.
8. **Dev mode.** `packs.dev_set {path}` (absolute folder) loads each subfolder with a `halp-pack.json` as an unsigned `dev` pack with id `dev.<id>` and role `dev-<role>`; it is not persisted (a restart turns it off), its types are recorded as retired so items stay readable. `packs.dev_reload` re-reads the folder (`conflict` when off); `packs.dev_get` returns `{path, packs, errors: [{dir, message}]}`.
9. **Keys.** `packs.keys_list` lists first-party keys (compiled in, not revocable) and user-trusted keys with how many packs are pinned to each. `packs.keys_add {pubkey_b64, label}`: 32-byte Ed25519 key, label 1–100 characters; a duplicate or a first-party key is `conflict`. `packs.keys_revoke {key_id}` marks it revoked and disables every pack pinned to it (`disabled_packs`); revoking a first-party key is `denied`; such packs cannot be enabled again.
10. **Tier C lookups** (desktop shell, not commands): `Core::ext_ui_widget(pack_id, widget) -> Option<ExtUiWidget {kind, calls, entry, trust}>` and `Core::ext_ui_file(pack_id, widget, path) -> Option<ExtFile {bytes, mime, sha256}>`. Both return `None` unless the pack is loaded, enabled and of a trust that may run code. `entry` is the full bundle path (`<root>/<entry>`); a file must lie strictly under the widget's `root/`, be listed in the manifest's file index with a UI mime type, and match its SHA-256 again when served.

### Review fixes: what a pack change does to existing items
11. **Every item is checked.** Any change that changes or removes the definition of a type with items (`install` of an update, `enable`, `disable`, `uninstall`, `rollback`, `keys_add`) validates every item of each such type against the registry it would leave behind, including the inherited `type_overrides`; any item that would fail makes the change `conflict` ("N items would no longer validate (ids…); nothing was changed. First: …", up to 50 ids). Rollback validates all items of the affected types, not only the ones the update migrated. The preview of an update shows the refusal as a warning ("It cannot be installed as it is: …"). **Deviation from the plan's "retire" rule (§3.7):** an update that drops a type, or drops an override, that items still need is refused instead of retiring the type; an uninstall or disable that leaves items valid against the retired definition still retires it as in note 7.
12. **`keys_revoke` is never refused.** Its result gains `invalid_items: string[]`: items that no longer validate once the key's packs are disabled (for example because an override is gone). They keep their data; the user edits them back in line.
13. **Data classes do not move.** An update (signed or unsigned) or rollback that changes the `x-halp-data-class` of a type id that stays is `conflict` ("task type … would change its data class from … to …; a pack change may not move items between data classes"). A migration `retype` must target a type of the same class: checked when the manifest is validated (the bundle is rejected) and again at apply ("item … would move from data class … to …"). In `permission_diff`, a class change on a type that stays is always in `added` as `{kind: "data_class", id: <type_id>, detail: "<old> -> <new>"}` and never in `removed`, so a weakened class reads as an escalation.
14. **Lock rules do not change under locked items.** An update or rollback that changes or removes the `x-halp-immutable-when` of a type with locked items is `conflict` ("task type … has locked items (such as …); this would change or remove its x-halp-immutable-when rule and unlock them"). Overrides cannot carry it (they reject every `x-halp-*` key). Dev changes run notes 13 and 14 only, not note 11.
15. **Pins use the full fingerprint.** The pack record stores `key_fp` (64 hex) next to `key_id`; pins and revocation lists compare the full fingerprint, so a key whose 16-hex `key_id` collides does not match. Older records with only `key_id` are still honoured and gain `key_fp` on their next update.
16. **Override trust.** An `unsigned` or `dev` pack may override only types defined by `unsigned` or `dev` packs (`denied` otherwise). `PackPreview.overrides` lists the overrides the pack applies: `[{type_id, title|null, icon|null, property_descriptions, added_properties, added_enum_values}]`.
17. **Dev mode and installed items.** Dev mode is never saved, so no installed pack's item may rely on a dev override: while dev mode is on, `tasks.create`/`tasks.update` and integration writes of an item whose type is not a dev pack's also validate the fields without dev packs (`invalid_args` otherwise). While dev mode is on, `packs.preview`/`install`, `enable`, `disable`, `rollback`, `uninstall` and `keys_add` refuse with `conflict` ("turn dev mode off before changing installed packs or keys"); `keys_revoke` is never refused. As a backstop, `packs.dev_set` (including `null`) and `packs.dev_reload` refuse with `conflict`, naming the items, when an installed pack's item would stop validating. Items of dev packs' own types are not checked.
18. **Tier C files.** A ui widget's `entry` must end in `.html`. Files are served by extension from `html js mjs css png woff2 json`; SVG is not served.
19. **Undo and redo keep items valid.** `history.undo`/`history.redo` refuse with `conflict`, naming up to five item ids (never field values), when the step would leave an item it writes, or any item of a task type it redefines or removes, with fields its type rejects (dev-mode rule of note 17 included). Nothing is written.
20. **Unloaded types fail closed.** An item whose `type_id` names a type that is not loaded (a stored definition that no longer validates, a skipped pack type) is in data class `secrets`. A request that names a type that does not exist yet (`types.define` of a new id, `tasks.create` with an unknown `type_id`) adds no class; the command itself refuses an unknown type.
21. **A type change carries its items' classes.** `types.define`, and `history.undo`/`history.redo` of a step that changes a task type, are classed by the type's current class, the `x-halp-data-class` of the definition written and (for a step) of the one restored, and the class of every item carrying the type, ancestors included. An agent without those grants gets `not_found`, so it can neither reclassify such items nor probe their fields with schema changes.
22. **Key ids.** Trusted keys are stored under their 16-hex key id. `packs.keys_add` refuses a different key with an id already in the list, revoked or not (`conflict`); keys are never merged or replaced, and a revoked key stays revoked. Matching one given key takes a 64-bit second preimage, so this is accepted.
23. **Focus and counts.** `focus.set` of an item in a non-default class is logged as "Focused a private item". `history.list` shows agents every `focus.set` as "Set focus" and every `consent.*` event as "<verb>: a request", and redacts the events of deleted items (their class can no longer be checked) (these events name items that may have become private since; agents read requests with `consent.get`/`consent.list`, which check). `day.state` counts only items the caller may see, like its agenda. A pack install or update is classed against the registry it leaves, so a migration that retypes items into a type the new version brings is not logged as a private write.
